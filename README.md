# Лабораторная работа №2
Анализ веб-приложения и клиент-серверного взаимодействия
Цель работы

Изучить принцип взаимодействия компонентов современного веб-приложения на примере реального цифрового сервиса.

В ходе работы необходимо исследовать HTTP-взаимодействие между браузером и сервером, структуру запросов и ответов, использование cookies и взаимодействие Frontend, API и Backend.

# 1. Исследуемая информационная система

В качестве исследуемой информационной системы был выбран веб-сервис Notion.

Notion представляет собой облачный сервис для создания и редактирования страниц, заметок, документов и организации информации в рабочих пространствах.

Исследование проводилось непосредственно через веб-интерфейс сервиса и инструменты разработчика браузера.

#1.1. Сценарий взаимодействия

Для исследования был выбран следующий сценарий:

Пользователь создаёт новую страницу в Notion и добавляет на неё текстовый блок.

Данный сценарий позволяет проследить полный путь изменения от действия пользователя в интерфейсе до формирования HTTP-запроса к серверу.

В рамках первой лабораторной работы уже была исследована HTML-структура страницы и отдельных редактируемых элементов.

В данной лабораторной работе основное внимание уделяется уже не HTML-разметке, а сетевому взаимодействию.

# 1.2. Инструменты исследования

Для анализа использовались встроенные инструменты разработчика браузера.

Основным инструментом стала вкладка Network, с помощью которой можно просматривать:

отправленные HTTP-запросы;
HTTP-методы;
адреса запросов;
коды ответов;
передаваемые параметры;
содержимое HTTP-ответов.

Также были изучены cookies, используемые веб-приложением.

# 2. Анализ HTTP-запросов
# 2.1. Перехват сетевых запросов

После открытия инструментов разработчика и перехода во вкладку Network были выполнены действия в интерфейсе Notion: создание страницы и добавление текстового блока.

В результате браузер сформировал несколько сетевых обращений.

Наиболее важным для исследования оказался запрос, связанный с сохранением изменений страницы.

На данном этапе можно увидеть список обращений браузера к серверам веб-приложения.

Для дальнейшего анализа был выбран запрос saveTransactionsFanout.

# 2.2. Основной HTTP-запрос

Основной исследованный запрос имеет следующий вид:

Метод:

POST

Адрес:

https://app.notion.com/api/v3/saveTransactionsFanout

Таким образом, браузер отправляет данные на API Notion с использованием HTTP-метода POST.

Использование POST соответствует характеру операции, поскольку запрос используется для передачи данных на сервер.

В запросе также зафиксирован код ответа:

200 OK

Это означает, что сервер успешно обработал обращение.

# 2.3. Структура URL запроса

Адрес исследованного запроса состоит из нескольких частей:

https://app.notion.com/api/v3/saveTransactionsFanout

В нём можно выделить:

https — используемый защищённый протокол;
app.notion.com — домен сервиса;
/api/v3/ — путь к API;
saveTransactionsFanout — конкретная операция API.

Таким образом, браузер обращается не непосредственно к HTML-странице, а к отдельному API-методу.

# 2.4. Назначение запроса

По названию saveTransactionsFanout и характеру передаваемых данных можно установить, что запрос используется для передачи изменений, выполненных пользователем.

В рассматриваемом сценарии такими изменениями являются создание страницы и добавление текстового блока.

При этом внутренний алгоритм обработки данного API-метода со стороны сервера в рамках лабораторной работы не исследовался.

Поэтому достоверно можно утверждать именно то, что браузер отправляет запрос с указанным адресом и параметрами, а сервер возвращает успешный ответ.

# 3. Анализ HTTP-ответов
# 3.1. Код ответа сервера

Для исследованного запроса сервер возвращает код:

200 OK

Код 200 означает успешную обработку HTTP-запроса.

Это позволяет сделать вывод, что запрос saveTransactionsFanout был принят сервером и обработан без HTTP-ошибки.

# 3.2. Тело HTTP-ответа

В разделе Response был исследован непосредственно ответ сервера.

В результате был получен пустой JSON-объект:

{}

Таким образом, ответ состоит из:

HTTP-статуса 200 OK;
JSON-объекта {} в теле ответа.

В данном случае серверу не требуется передавать в ответе большое количество информации.

# 3.3. Взаимосвязь запроса и ответа

Общая последовательность взаимодействия выглядит следующим образом:

Пользователь изменяет содержимое страницы.
Frontend обрабатывает действие пользователя.
Браузер формирует POST-запрос.
Запрос отправляется на saveTransactionsFanout.
Сервер обрабатывает запрос.
Сервер возвращает 200 OK.
В теле ответа находится {}.
Клиент продолжает работу с интерфейсом страницы.

Таким образом, HTTP-запрос и ответ являются частью единого цикла клиент-серверного взаимодействия.

# 4. Анализ передаваемых параметров
# 4.1. Payload HTTP-запроса

Для более подробного анализа был открыт раздел Payload исследуемого POST-запроса.

В передаваемых данных присутствуют поля, связанные с выполняемой операцией.

В частности, были обнаружены:

requestId;
transactions;
id;
spaceId;
другие внутренние параметры сервиса.

# 4.2. Параметр requestId

requestId представляет собой идентификатор конкретного запроса.

Его наличие позволяет отличать одну операцию от другой и использовать идентификатор внутри механизма обработки запроса.

Точное внутреннее назначение данного параметра со стороны сервера по результатам только сетевого анализа установить нельзя.

# 4.3. Параметр transactions

В запросе присутствует массив transactions.

Он содержит данные, связанные с изменениями, которые необходимо обработать серверу.

Для исследуемого сценария изменения связаны с действиями пользователя при создании страницы и добавлении блока.

Таким образом, клиент передаёт серверу не просто текстовую команду, а структурированные данные об изменениях.

# 4.4. Идентификаторы страницы и рабочего пространства

В передаваемых данных присутствуют внутренние идентификаторы, среди которых был обнаружен spaceId.

Также в структуре данных присутствуют идентификаторы объектов.

Они используются приложением для указания объектов, к которым относятся выполняемые операции.

При этом точное назначение всех внутренних идентификаторов невозможно определить только по наблюдаемому запросу, поэтому в работе не делаются предположения о параметрах, назначение которых непосредственно не установлено.

# 5. Анализ Cookies
# 5.1. Получение Cookies

Для исследования состояния клиента были просмотрены cookies, связанные с веб-приложением Notion.

Cookies являются небольшими фрагментами данных, которые браузер хранит для определённого сайта и которые могут использоваться при последующих обращениях.

# 5.2. Назначение Cookies

Cookies могут использоваться веб-приложением для различных задач:

хранения состояния пользовательской сессии;
идентификации пользователя или устройства;
хранения настроек;
обеспечения работы механизмов авторизации;
передачи служебной информации при обращении к серверу.

В ходе исследования было установлено наличие cookies у сайта Notion.

При этом содержимое и точное назначение каждой конкретной cookie не рассматриваются подробно, поскольку для этого потребовалась бы дополнительная документация сервиса.

# 6. Взаимодействие Frontend, API и Backend
# 6.1. Frontend

Frontend представляет клиентскую часть веб-приложения, с которой непосредственно взаимодействует пользователь.

В рассматриваемом сценарии Frontend отвечает за отображение страницы Notion и обработку действий пользователя.

Когда пользователь создаёт страницу и добавляет блок, действие сначала происходит на стороне клиентского интерфейса.

# 6.2. API

После изменения данных клиент формирует запрос к API.

В исследованном случае это:

POST /api/v3/saveTransactionsFanout

API выступает в качестве интерфейса, через который клиентская часть взаимодействует с серверной частью приложения.

# 6.3. Backend

После получения запроса API передаёт его на обработку серверной части приложения.

Backend обрабатывает полученные данные и выполняет соответствующие серверные операции.

В рамках данной лабораторной работы внутренняя реализация Backend не исследовалась.

Поэтому на архитектурной схеме Backend рассматривается как компонент серверной части, существование которого следует из клиент-серверной модели приложения, а не как непосредственно исследованный программный модуль.

# 6.4. Результат взаимодействия

После обработки запроса сервер возвращает клиенту:

200 OK

и тело ответа:

{}

После этого Frontend продолжает работу с интерфейсом Notion.

Таким образом, взаимодействие можно представить в виде:

Пользователь → Frontend → API → Backend → API → Frontend → Пользователь
